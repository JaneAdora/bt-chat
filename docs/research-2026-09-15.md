# Offline phone-to-phone chat: research briefing

Date: 2026-09-15. Three parallel research passes: BitChat status, existing apps, technical options. Verified claims carry source URLs; anything marked (inferred) is a judgment call.

## 1. BitChat status

- Open source. Android repo is GPL-3.0 (LICENSE.md; README still says public domain, trust the LICENSE). iOS repo is Unlicense. https://github.com/permissionlesstech/bitchat-android
- Actively maintained. Android v2.0.1 released 2026-08-11, commits into September. On Google Play (com.bitchat.droid, 3.7 stars) and GitHub APKs. Not on F-Droid.
- Design: every phone is BLE GATT central and peripheral at once. Custom flood relay with TTL 7, dedup LRU, ~469 byte fragments, Noise XX encryption, store and forward, Nostr fallback over internet. Geohash location channels. It is designed for crowds and protests, not for two people.
- Reliability: peer discovery failures are the top complaint, several on Samsung (issues #1, #214, #124 Android 16 sleep bug, #45 two Pixels see zero users). Delivery: #194 intermittent non-delivery, #193 reconnecting peer becomes unreachable. Most remain open with no maintainer reply. 2026 releases claim reconnect fixes but the issues are not triaged, so unclear if fixed.
- Security: July 2025 MITM identity spoofing (Radocea), Trail of Bits confirmed plus weak forward secrecy and a buffer overflow. v1.5.4 (June 2026) cites audit fixes, v1.7.1 binds Noise sessions to identity. Audit report itself not published.
- Security, July 2026: the Android repo carries docs/security-review-jul-27.md, an internal static review listing 2 critical and 12 high findings, including Noise shared secrets and decrypted DM text written to logcat in release builds, a pre-auth decompression bomb, a broken replay window, and "first announce wins" peer-ID impersonation. Spot checks show several are fixed on main and 2.0.1 cites identity binding and bounded payloads, but not every finding was verified. https://github.com/permissionlesstech/bitchat-android/blob/main/docs/security-review-jul-27.md
- Useful Android design docs exist in the repo: NOISE_PEER_ID_BINDING.md, SOURCE_ROUTING.md, ANNOUNCEMENT_GOSSIP.md, file_transfer.md, and a device-transport-test-matrix.md that requires two physical phones from different manufacturers.
- Direction: hybrid mesh plus Nostr platform, ecash, Wear OS, PTT voice. Adoption driven by protests (Nepal, Madagascar, Iran, India takedown demand July 2026). No serious competing fork.

Sources: whitepaper https://raw.githubusercontent.com/permissionlesstech/bitchat/main/WHITEPAPER.md, Trail of Bits https://blog.trailofbits.com/2025/07/18/building-secure-messaging-is-hard-a-nuanced-take-on-the-bitchat-security-debate/

## 2. Can a PWA do this? No.

- Web Bluetooth is central-only, GATT-client-only. A web page cannot advertise or act as a peripheral. Peripheral mode is not on the roadmap. https://github.com/WebBluetoothCG/web-bluetooth/blob/main/implementation-status.md
- Two phones running only PWAs are both centrals with nothing to connect to. Browser-only Bluetooth chat is impossible.
- Web Bluetooth also needs HTTPS, a tap gesture, and dies when the tab is frozen or screen is off. Samsung Internet supports it, but that does not help. Web Serial is unsupported in Samsung Internet.
- The only web-only path that works: hotspot plus a local server. Jane's phone (the one with a SIM) runs a hotspot with no upstream needed; Android hotspot is a real LAN and clients can reach the host. A small Node server in Termux on Jane's phone serves a plain http page with WebSockets; kid's Samsung browses to 192.168.x.x. Caveats: some Samsung firmware refuses to start the Settings hotspot without a SIM, so the kid's phone cannot host. No service worker or home-screen install over plain http on a LAN IP (would need mkcert and a CA installed on the kid's phone). Battery cost of hotspot on Jane's phone. "Connected, no internet" banner but clients stay attached.

https://briarproject.org/quick-start/

https://github.com/getknit/knit

Recommendation before building: install Briar and Knit on both phones, test whether they reconnect after both phones sleep 10 minutes.

## 4. If we build it: native Android is the real answer

### Bluetooth Classic RFCOMM (SPP). Simplest and most reliable for two Android phones.
- Stream socket like TCP. BluetoothServerSocket on one side, BluetoothSocket on the other; either phone can run both. Shared UUID.
- Pairing dialog appears once, then it is a bond and reconnects silently. Insecure variants skip the dialog entirely (link still encrypted on BT 2.1+).
- Throughput 150 to 200 KB/s in practice. Images are trivial: length prefix plus bytes.
- Permissions on Android 12+: BLUETOOTH_SCAN (neverForLocation), BLUETOOTH_CONNECT, BLUETOOTH_ADVERTISE only for discoverable mode. One "Nearby devices" runtime prompt.
- Needs a foreground service to stay alive with screen off.
https://developer.android.com/develop/connectivity/bluetooth/connect-bluetooth-devices

### BLE GATT. What BitChat uses. Buys nothing over RFCOMM for two phones except pain.
- MTU up to 517, realistic 30 to 100 KB/s with tuning. GATT error 133 is generic; Samsung stacks time out at ~10 s and sometimes need the Bluetooth cache cleared. Background scanning is restricted.

### Google Nearby Connections. Black box that does it all.
- Still live (docs updated June 2026). Auto-negotiates BT Classic, BLE, Wi-Fi Direct/hotspot. Fully offline, encrypted, ~100 m stated range. Payloads: BYTES (32 KB), FILE (any size), STREAM. P2P_POINT_TO_POINT for 1:1 is the fastest and most stable strategy. Needs Google Play Services (fine on Samsung) and Location on.
https://developers.google.com/nearby/connections/android/get-started

### Framework fit for a JS/TS person
- Capacitor: no maintained plugin offers an RFCOMM server. BLE peripheral exists in @capgo/capacitor-bluetooth-low-energy (Jun 2026). Would mean writing a small native plugin.
- React Native: react-native-bluetooth-classic (Nov 2025) supports accept/server mode on Android. expo-nearby-connections pushed Aug 2026. BLE peripheral is dead.
- Flutter: flutter_blue_classic (Android-only Classic), flutter_ble_peripheral 3.1.0 (Sep 2026), nearby_connections 4.3.0 (19 months stale).
- Kotlin/Compose: Google's BluetoothChat sample is archived. Community references: BTConnect (pushed Sep 2026, chat + files + voice) https://github.com/thakur-ritik/BTConnect and bluetooth-chat-mvvm (2023).

## 5. Bluetooth primer

- Classic (BR/EDR): point-to-point streaming radio, up to 3 Mb/s. Used for audio and serial. Think "wireless cable."
- BLE: burst-oriented, low power, tiny packets. Roles: peripheral advertises and hosts a GATT server (a table of small values); central scans and connects as client. Think "wireless sensor that you poll."
- Pairing is the one-time key exchange. Bonding is storing those keys. Connecting is any later session.
- Indoor range: about 10 m rule of thumb; walls cut it hard. Same room reliable, adjacent room usually, across a house no.
- iOS is harder: Classic SPP needs Apple's MFi program. BLE does not. This is why BitChat and most mesh apps use BLE, and why Android-only lets us use Classic.
- "Mesh" in BitChat is a custom multi-hop relay over BLE connections, not SIG Bluetooth Mesh (which phones do not implement as nodes).
